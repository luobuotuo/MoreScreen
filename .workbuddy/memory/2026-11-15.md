## 晚间攻坚（13:5x → 20:5x，提交 5e8a8e6）：丢帧问题排查

**起因**：平板显示「丢帧 z 持续上涨」，帧率只有 13-14fps（发送 20fps），丢包为 0。

**排查链路（逐层排除，最终定位到浏览器渲染层）**：

| 层 | 验证手段 | 结论 |
|---|---|---|
| 采集侧 | 新增 `capture-diag` 命令 | 60fps 稳定，30 秒 1802 帧零丢帧零重复 |
| 编码侧 | 30 分钟运行统计 | 产出 36009 AU（20fps×1800s），背压仅丢 15 帧 |
| 传输侧 | 丢包 0%、RTT 5ms、节拍器 50ms 精确 | 干净 |
| 时间戳 | 检查 webrtc-rs 源码 | RTP 时间戳 CFR 正确，无漂移 |
| 接收端 | `requestVideoFrameCallback` 上屏帧率 | **稳定 13-14fps，恒定 70% 比例** |

**关键铁证**：`framesDecoded == framesReceived`（608==608）但 `framesDropped == 262`（43%）。
帧**全部解出来了，只是没全部上屏** → 是浏览器渲染层丢弃，不是传输/解码问题。

**恒定 70% 比例**：20fps→14、15fps→10、10fps→7，与帧率/码率/丢包全无关，
疑似华为浏览器（鸿蒙内核）WebRTC 视频渲染节流。**非宿主代码可解**。

**本次有效成果**（已提交）：
1. RTX 重传三件套（rtx codec + enable_sender_rtx + read_rtcp 主动驱动），SDP 里 `a=ssrc-group:FID` 补齐
2. 绝对节拍器 `tokio::time::interval` 替代来帧即发
3. 接收端统计重做 + `【上屏】` 真实帧率探针 + `【raw】` 诊断日志
4. WS 读线程 20ms 超时修复死锁
5. 会话重建竞态修复（answer 代际守卫 + restart 500ms 防抖）
6. `capture-diag` 采集诊断命令

**自己制造又绕回的混乱**（教训）：GOP 砍半→码率暴涨；wallclock 时间戳→双时钟打架；
`sender.send()` 手动调用→answer 后 Closed；节拍器排空队列→micro-burst。均已回滚。

**已知遗留（未解决）**：
1. ~~华为浏览器渲染层恒定丢帧 30%~~ → **已随多客户端重构消失**，见下节
2. ~~多客户端互相踢~~ → **已重构解决**，见下节

**下一步方向**：
1. 换非鸿蒙接收端（iPad Safari / 安卓 Chrome）验证上屏帧率上限是否消失
2. 若确认是渲染上限，评估是否值得为高帧率场景做优化

## 深夜第二轮（22:0x → 23:1x）：多客户端架构重构 + 丢帧归零

### 用户决策
跳过"换设备验证"，直接按 A 方案（每客户端独立 PeerConnection）重构，然后进入 P2。

### 重构内容（提交后生效）

| 层 | 改动 |
|---|---|
| `serve.rs` | 客户端加唯一 `ClientId`；`poll_inbox` 返回 `(id, text)`；新增 `send_to(id, text)` 定向发送；新增 `poll_joined()/poll_disconnected()` 生命周期队列；删除 `peer_gen` 代际机制 |
| `webrtc.rs` | `WebRtcHandle` → `WebRtcHub`：`HashMap<ClientId, SessionHandle>`，每客户端一个独立 PeerConnection + 独立 tokio 线程 + 独立 frame/signal 通道；每会话一个轻量信令转发线程（补 client_id 汇入总通道，使 `run_once` 无需感知 id）；删除 `SessionEnd`/`run_session` 重建循环；`SignalIn` 去掉 `Restart` |
| `main.rs` | 信令泵改为：轮询 joined→`join(id)`、disconnected→`leave(id)`、信令 `(id, sig)`→`send_to(id)`、inbox `(id, text)`→`deliver(id)`；移除 restart 防抖 |
| `capture.rs` | 新增 `include_cursor` 参数 + `SetIsCursorCaptureEnabled`；`--no-cursor` 开关 |
| `webrtc.html` | 新增「1:1 原始尺寸」按钮（排除非整数缩放）、`【上屏】` 真实帧率探针、`【raw】` 诊断转储 |

### 关键结论（更正前一轮的误判）

**丢帧问题随架构重构自行消失**：
- 重构前：`帧率 13-14 / framesDropped 持续涨 / 恒定 30-43%`
- 重构后：`帧率 20(=发送值) / framesDropped = 0 / 丢包 0%`

**所以"华为浏览器渲染层恒定丢帧 30%"是误判**，真因是旧架构的 restart 竞态反复打断会话，
每次重连丢一批帧累计成那个恒定比例。

### 剩余问题：上屏帧率上限 ~30-35fps（非宿主可解）

| 发送帧率 | 平板上屏 | 比例 |
|---|---|---|
| 20 fps | 13-14 | 68% |
| 60 fps | 29-35（全屏也一样） | 50-58% |

`framesDecoded` = 全部帧、`framesDropped` = 0 → **解码完整，是渲染层主动跳帧**。

已排除的因素：
- 智能刷新率（固定 120Hz 后仍晃）
- 非整数缩放（1:1 原始尺寸仍晃）
- 光标合成（`--no-cursor` 仍晃）
- DPI（虚拟屏 100%）
- 解码能力（framesDropped=0）
- 全屏节流（全屏后 29-35 无改善）

**结论**：华为浏览器（鸿蒙内核）对 WebRTC 实时视频的合成频率约 30-35fps，非宿主代码可控。
静止画面不抖、完全清晰 → 桌面/文档/代码场景可用。
