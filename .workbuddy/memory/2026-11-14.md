### 踩坑清单（H.264 流式传输，务必记住）
1. 访问单元**不能按 NAL 切**：SPS/PPS 必须与它描述的图像帧同包，否则浏览器解不出 IDR。
2. ffmpeg/libx264 走 global_header 时 **SPS/PPS 只在码流开头出现一次** → 必须缓存并给每个关键帧补齐。
3. 客户端中途接入**拿不到关键帧** → 缓存最近关键帧，新客户端接入即补发。
4. `VideoDecoder.isConfigSupported()` **返回 Promise**，当同步值用会永远 undefined → 误判"不支持 H.264"。
5. 解码器 configure 完成前**不能丢首包**（关键帧）→ 先排队再补喂。
6. 诊断代码每帧刷 title 会**覆盖真实错误信息** → 错误要放独立字段。
7. Chromium 报 `EncodingError: Decoding error.` 时，先用 VP8 做对照，再怀疑自己的码流。

## 11-15 11:3x — 新增 scripts/run_stream.cmd（流服务启动器）

**背景**：用户在管理员 cmd 直接敲 `rs-host stream ...` 报"不是内部或外部命令"——
rs-host.exe 从不在系统 PATH 中（只在构建目录 `%LOCALAPPDATA%\Temp\rs-target\release\`），
我们一直用完整路径或 `cargo run` 调用，但对外说明时写成了裸命令名。

**踩到的两个 Windows 批处理坑（都已修复）**：
1. **`.cmd` 必须是 CRLF**：Write 工具默认写 LF，cmd 会把 `REM` 注释行当命令执行
   （报 `'默认:' 不是内部或外部命令`）。`.gitattributes` 已有 `*.cmd text eol=crlf`，
   但**新文件首次写入时该规则不生效**，必须写完手动转 CRLF。
2. **`chcp 65001` + 中文 echo 不可靠**：cmd 切到 UTF-8 代码页后，含中文的 echo 行
   会被错误解析（`'程序:' is not recognized`）。最终脚本改为**纯 ASCII 输出**，彻底避开。

**验证**：脚本启动后 8787/8788 均监听、页面 HTTP 200（6381 字节）、WS 探针 9.8 MB/s；
`rs-host` 打印的接收端地址为 `http://192.168.0.104:8788/`。
