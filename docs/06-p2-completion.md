## 二、关键技术决策（含取舍理由）

### 2.1 为什么画质协商不做"运行时改码率"

现状：H.264 编码由**外部 ffmpeg 进程**完成（QSV），码率通过启动参数 `-b:v` 固定。

三个候选方案：

| 方案 | 可行性 | 代价 |
|---|---|---|
| 运行时改 ffmpeg 码率 | ❌ 不支持——ffmpeg 无运行时改编码参数的接口 | — |
| 检测到拥塞就重启编码器 | ✅ 可行 | 每次调整 **1~2 秒黑屏**，且会打断所有会话 |
| 只上报 + 建议（本实现） | ✅ | 需要人工按建议重启，但**零中断** |

**决策**：采用第三种。接收端上报的真实数据（丢包率、上屏帧率）比任何估算都准，
宿主打印明确建议（如「丢包 >3%，建议降码率」），由用户决定是否重启。
后续若要自动化，正确路径是**进程内自研编码器**（roadmap 已列为 P4 方向），
届时才能真正做到无中断动态码率。

### 2.2 为什么自己写 QR 编码器

局域网无外网，不能调用在线二维码 API；引入第三方库会增加静态体积与供应链风险。

自研范围（有意收窄以保可靠）：

- **Byte 模式** + **版本 3（29×29）** + **纠错 L**（55 数据码字 / 15 纠错码字）
- 容量上限 53 字节，足够编码 `http://192.168.0.107:8788/webrtc.html`（34 字节）
- **固定掩码 0**：QR 标准要求解码器支持全部 8 种掩码，固定一种完全合法，
  省掉整段罚分计算，显著缩小出错面

**验证方式**（`node` 单测，已通过）：

```
尺寸 29                    ✅
定位图形 1111111/1011101   ✅
定时图形 10101 交替        ✅
暗模块 (21,8) = 1          ✅
对齐图形 (20,22)=1 (22,22)=1 (21,22)=0  ✅
formatInfo(0) = 0x77C4     ✅ 与 QR 标准值完全一致
超长内容返回 null          ✅
```

`formatInfo(0) = 0x77C4` 是最关键的验证——它同时核对 RS/BCH 生成多项式与固定异或掩码，
这一项对了，说明纠错与格式信息链路是正确的。

### 2.3 输入回传为什么默认关闭

`SendInput` 能完全控制主机（含键盘输入）。默认开启意味着「任何能打开该页面的人都能操作你的电脑」。

**决策**：

- 宿主必须显式 `--allow-input` 才真正注入事件（未开启时 `handle_ctl` 直接 return）
- 接收端还有第二道闸：必须点「控制本机」按钮才发送输入事件
- 两道闸互相独立，任一道关闭都不会产生实际控制

坐标口径：接收端发**画面内归一化坐标 0~1**（平板不知道虚拟屏在桌面中的位置），
宿主换算为 `目标屏 bounds + 归一化 × 目标尺寸`，再转成 `SendInput` 的 0~65535
并带 `MOUSEEVENTF_VIRTUALDESK`，因此虚拟屏摆在任意位置（含负坐标）都正确。

### 2.4 为什么用 DataChannel 而不是 WebSocket 传控制消息

- 与媒体走同一传输路径，不受 WS 单连接阻塞影响
- 延迟更低（无 WS 帧头与 JSON 编解码排队）
- 天然按会话隔离——每个 `PeerConnection` 有自己的一条 `ctl` 通道

## 三、使用方法

### 3.1 宿主启动

```bash
# 基础（只观看）
rs-host stream-webrtc --display MttVDD --mode 1280x720@60 --fps 30 --bitrate 1500

# 允许平板控制本机
rs-host stream-webrtc --display MttVDD --mode 1280x720@60 --fps 30 --bitrate 1500 --allow-input

# 关闭光标合成（对照排查用）
rs-host stream-webrtc --display MttVDD --fps 30 --no-cursor
```

启动后终端会打印：

```
WS 信令     : ws://192.168.0.107:8787
接收端页面  : http://192.168.0.107:8788/webrtc.html
扫码配对页  : http://192.168.0.107:8788/pair.html   ← 在平板上打开此页扫二维码
```

### 3.2 接收端（平板）

**首次连接**：平板浏览器打开 `http://<主机IP>:8788/pair.html` → 扫页面上的二维码
→ 直接跳到接收端 → 点「开始接收」。

**日常使用**：直接打开接收端地址 → 点「开始接收」→ 自动全屏 + 屏幕常亮。

**控制本机**：点页面上的「控制本机」按钮 → 触摸即控制鼠标；长按 500ms = 右键；
键盘输入直接转发（需宿主带 `--allow-input`）。

### 3.3 参数速查

| 参数 | 作用 |
|---|---|
| `--display <子串>` | 选显示目标（匹配 label / 设备路径 / 适配器 ID） |
| `--mode WxH[@Hz]` | 切换虚拟屏模式，如 `1280x720@60`。**不传则不动桌面布局** |
| `--fps N` | 编码帧率 |
| `--bitrate K` | 目标码率（kbps） |
| `--no-cursor` | 采集时不合成鼠标光标 |
| `--allow-input` | 允许接收端控制本机（默认关） |

虚拟屏可用分辨率（实测枚举）：`800x600` / `1280x720` / `1366x768` / `1920x1080` /
`2560x1440` / `3840x2160`，各档均支持 30/60/90/120/144/165Hz。

## 四、已知限制（如实记录）

### 4.1 1220x720@60fps 编码吞吐不足（实测）

| 分辨率×帧率 | 采集帧数 | 编码产出 | 产出率 |
|---|---|---|---|
| 800x600@60 | 216176 | 216176 | 100% |
| 1280x720@60 @2500kbps | 216172 | 202012 | **93.5%** |
| 1280x720@60 @1500kbps | 216152 | 201873 | **93.4%** |

产出率与码率无关，是「1280x720 单帧 3.7MB × 60fps = 221MB/s」超出当前
D3D11 回读 + QSV 编码的吞吐。**建议该分辨率配 30fps**（编码压力减半）。

### 4.2 上屏帧率与发送帧率的匹配关系（结论已修正）

实测（华为平板 + 华为浏览器）：

| 发送帧率 | 上屏帧率 | 呈现率 | `framesDropped` |
|---|---|---|---|
| 20 fps | 13-14 | 68% | 0 |
| 30 fps | **30.0** | **100%** | 0 |
| 60 fps | 29-35 | 55% | 0 |

**结论修正**：这不是「渲染上限 30-35fps」的缺陷，而是**30fps 正好是这台平板的渲染工作点**。
30fps 下每一帧都完整呈现（100%），60fps 反而因为要跳帧而只有 55%。

**因此默认配置定为 30fps 是正确选择，不是妥协。**

已排除的影响因素：智能刷新率（固定 120Hz）、非整数缩放（1:1 原始尺寸）、
光标合成（`--no-cursor`）、DPI（100%）、全屏节流。

**静止画面完全不抖、文字清晰**，桌面/文档/代码场景可用。

### 4.3 画质协商未真正闭环

见 2.1：只上报建议，不自动改码率。真正的自适应需要进程内编码器。

### 4.4 键盘映射仅覆盖常用键

`KEYMAP` 覆盖回车/退格/方向/功能键/字母数字，未覆盖组合键修饰符语义
（如 `Ctrl+C` 会分别按下 Ctrl 和 C，多数场景可用，但少数需要修饰符状态机的应用可能异常）。

## 七、后续修复记录（2026-11-19 ~ 11-20 实测发现）

P2 交付后连续出现四个独立问题，逐一定位并修复。**它们是四个不同的 bug，不是同一个问题的反复**。

### 7.1 连接黑屏：`renderState is not defined`（提交 `913bfa0`）

P2.7 在 `buildPeerConnection()` 里调用了 `renderState('connecting')`，
但函数定义在编辑过程中被漏掉。

故障链：收到 offer → `buildPeerConnection()` → `ReferenceError` →
**answer 永远不生成** → 宿主 `conn` 停在 `New` → 平板黑屏。

**教训**：`new Function()` 语法检查查不出「引用未定义标识符」这类运行时错误。
前端改动必须做一次浏览器运行时验证（抓 `pageerror`）。

### 7.2 扫码无反应：QR 格式信息位置写错（提交 `ebe3365`）

`qr.js` 里格式信息的垂直部分误写成 `setF(14 - i, 8, bit)`，
`i=8..14` 时行号落在 6..0，**写进了左上定位图形区域**；正确应为 `setF(SIZE-15+i, 8, bit)`（行 22..28）。

后果：扫描器读不到纠错等级/掩码 → 整张码无法解码。

**验证方式升级**（结构检查发现不了位置错误）：
反向读取矩阵 → 格式信息两处镜像位置均读出 `0x77C4`；
反向 zigzag 提取 70 个码字 → **RS 自校验通过**（任何一格错位都会破坏校验）；
解析出 `0100` Byte / 37 字节 / 与原 URL 完全一致。

### 7.3 新版 Chromium 连不上：DTLS 曲线协商缺陷（提交 `da64a16`）★ 最重要

**现象**：`ICE connected` 但 `connection failed`，画面全黑。旧内核浏览器（华为浏览器）正常，
新版 Edge/Chrome 必失败。

**定位过程**：先用浏览器 `getStats()` 确认 Edge 已选中 `127.0.0.1` loopback 候选且
`nominated`（排除网络/代理干扰），再开 `RUST_LOG=webrtc_dtls=trace` 拿到：

```
Flight 0 result alert: Some(Fatal / IllegalParameter), err: Some(ErrInvalidNamedCurve)
Failed to start manager dtls: invalid named curve
```

**根因**：`webrtc-dtls 0.11` 的 `flight0.rs` 只取客户端 `supported_groups` 的**第一个**曲线：

```rust
state.named_curve = e.elliptic_curves[0];   // 不遍历！
```

新版 Chromium 把后量子混合曲线 `X25519MLKEM768 (0x11ec)` 排在首位，
`NamedCurve::from(0x11ec)` 得到 `Unsupported` → `generate_keypair()` 报
`ErrInvalidNamedCurve` → 握手直接失败。RFC 5246 要求遍历选取双方都支持的曲线，
上游 `webrtc-dtls 0.12.0` 已按此修正。

**修复**：`webrtc-rs 0.12` 的依赖约束是 `^0.11`，无法直接升版本，故
**vendor 一份 0.11（903K）只改这一段**为遍历选取，用 `[patch.crates-io]` 指向 `vendor/webrtc-dtls`。

**验证**：修复前本机 Edge 必失败；修复后

```
connectionState: connected / iceConnectionState: connected
[webrtc] #1 诊断 conn=Connected ice=Connected
```

**长期影响**：Chrome/Edge 会越来越普遍默认启用 PQ 曲线，所有基于 webrtc-rs 0.12 的项目都会踩到，
建议后续关注上游把 webrtc-rs 依赖提到 webrtc-dtls 0.12+，届时可移除 vendor。

### 7.4 附带改进

- **loopback ICE 候选**（`set_include_loopback_candidate(true)`）：本机自测可走 127.0.0.1，
  绕开网卡地址路径；对局域网其它设备无副作用（它们探测失败后忽略）。
- **env_logger**：默认 `warn` 静默；排查用 `RUST_LOG=webrtc_dtls=trace,webrtc=info`。
  这是本次能定位 DTLS 根因的关键工具，建议保留。

### 7.6 同一浏览器多标签并发导致上屏帧率骤降（2026-11-21 实测）

**现象**：平板操作时画面拖动卡跳。宿主日志显示同时有 4 个客户端连接，上屏帧率分化严重：

| 客户端 | 上屏帧率 | jitterBuffer | RTT | 丢包 |
|---|---|---|---|---|
| #3 | 26~28 fps | 214~219 ms | 7~20 ms | 0% |
| #2 | 12.0 fps | 52 ms | 2~10 ms | 0% |
| #4 | 10.0 fps | 290~359 ms | 2~11 ms | 0% |

**根因**：不是网络（丢包全 0%、RTT 正常），是**接收端解码/渲染被拖垮**。
同一浏览器开多个 `webrtc.html` 标签页时，每个标签各自建立并解码一路 720p，
同一台设备并发解多路会抢 CPU/GPU；浏览器还会节流后台标签的渲染回调，
所以后台标签稳定掉到 10~12fps。用户关闭多余标签后立刻回到 **27~30fps**，根因确认。

**修复**：接收端加**同源多标签互斥**（`web/receiver/webrtc.html`）：
用 `BroadcastChannel` 探测，已有标签页处于接收状态时，新标签页的「开始接收」按钮
直接禁用并提示「请先关闭其它接收页」；旧标签页关闭后自动解锁。
`BroadcastChannel` 只在同源同浏览器内通信，所以**多设备（平板+电脑）不受影响**。
检查保持同步（不 `await`），以免丢失用户手势导致全屏被浏览器拒绝。

**验证**：`new Function` 语法检查通过；Edge headless 加载后按钮为初始态、
无 `Uncaught/ReferenceError/SyntaxError`。
**未验证**：双标签互斥的实际触发（headless 单进程构造不出同源双标签），需现场开两个标签确认。

**产品含义**：多设备同时观看是合法场景，因此只做「同浏览器互斥」而非全局限流；
但多设备并发仍会共享同一份编码输出，带宽随路数线性增长，属 P4 自适应码率要解决的问题。

> **2026-11-21 回退**：用户明确要求保留多标签能力（多开是正常用法），
> 该互斥已从 `webrtc.html` 移除。本节数据保留作为「多开时帧率会下降」的事实记录，
> 但不再做任何限制。**晃动问题的根因不在多标签**（单标签 27~30fps 时用户仍报告晃动），
> 另见下方排查。
