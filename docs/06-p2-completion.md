## 二、关键技术决策（含取舍理由）

### 2.1 为什么画质协商不做"运行时改码率"

现状：H.264 编码由**外部 ffmpeg 进程**完成（QSV），码率通过启动参数 `-b:v` 固定。

三个候选方案：

| 方案 | 可行性 | 代价 |
|---|---|---|
| 运行时改 ffmpeg 码率 | ❌ 不支持——ffmpeg 无运行时改编码参数的接口 | — |
| 检测到拥塞就重启编码器 | ✅ 可行 | 每次调整 **1~2 秒黑屏**，且会打断所有会话 |
| 只上报 + 建议（本实现） | ✅ | 需要人工按建议重启，但**零中断** |

**决策**：采用第三种。接收端上报的真实数据（丢包率、上屏帧率）比任何估算都准，
宿主打印明确建议（如「丢包 >3%，建议降码率」），由用户决定是否重启。
后续若要自动化，正确路径是**进程内自研编码器**（roadmap 已列为 P4 方向），
届时才能真正做到无中断动态码率。

### 2.2 为什么自己写 QR 编码器

局域网无外网，不能调用在线二维码 API；引入第三方库会增加静态体积与供应链风险。

自研范围（有意收窄以保可靠）：

- **Byte 模式** + **版本 3（29×29）** + **纠错 L**（55 数据码字 / 15 纠错码字）
- 容量上限 53 字节，足够编码 `http://192.168.0.107:8788/webrtc.html`（34 字节）
- **固定掩码 0**：QR 标准要求解码器支持全部 8 种掩码，固定一种完全合法，
  省掉整段罚分计算，显著缩小出错面

**验证方式**（`node` 单测，已通过）：

```
尺寸 29                    ✅
定位图形 1111111/1011101   ✅
定时图形 10101 交替        ✅
暗模块 (21,8) = 1          ✅
对齐图形 (20,22)=1 (22,22)=1 (21,22)=0  ✅
formatInfo(0) = 0x77C4     ✅ 与 QR 标准值完全一致
超长内容返回 null          ✅
```

`formatInfo(0) = 0x77C4` 是最关键的验证——它同时核对 RS/BCH 生成多项式与固定异或掩码，
这一项对了，说明纠错与格式信息链路是正确的。

### 2.3 输入回传为什么默认关闭

`SendInput` 能完全控制主机（含键盘输入）。默认开启意味着「任何能打开该页面的人都能操作你的电脑」。

**决策**：

- 宿主必须显式 `--allow-input` 才真正注入事件（未开启时 `handle_ctl` 直接 return）
- 接收端还有第二道闸：必须点「控制本机」按钮才发送输入事件
- 两道闸互相独立，任一道关闭都不会产生实际控制

坐标口径：接收端发**画面内归一化坐标 0~1**（平板不知道虚拟屏在桌面中的位置），
宿主换算为 `目标屏 bounds + 归一化 × 目标尺寸`，再转成 `SendInput` 的 0~65535
并带 `MOUSEEVENTF_VIRTUALDESK`，因此虚拟屏摆在任意位置（含负坐标）都正确。

### 2.4 为什么用 DataChannel 而不是 WebSocket 传控制消息

- 与媒体走同一传输路径，不受 WS 单连接阻塞影响
- 延迟更低（无 WS 帧头与 JSON 编解码排队）
- 天然按会话隔离——每个 `PeerConnection` 有自己的一条 `ctl` 通道

## 三、使用方法

### 3.1 宿主启动

```bash
# 基础（只观看）
rs-host stream-webrtc --display MttVDD --mode 1280x720@60 --fps 30 --bitrate 1500

# 允许平板控制本机
rs-host stream-webrtc --display MttVDD --mode 1280x720@60 --fps 30 --bitrate 1500 --allow-input

# 关闭光标合成（对照排查用）
rs-host stream-webrtc --display MttVDD --fps 30 --no-cursor
```

启动后终端会打印：

```
WS 信令     : ws://192.168.0.107:8787
接收端页面  : http://192.168.0.107:8788/webrtc.html
扫码配对页  : http://192.168.0.107:8788/pair.html   ← 在平板上打开此页扫二维码
```

### 3.2 接收端（平板）

**首次连接**：平板浏览器打开 `http://<主机IP>:8788/pair.html` → 扫页面上的二维码
→ 直接跳到接收端 → 点「开始接收」。

**日常使用**：直接打开接收端地址 → 点「开始接收」→ 自动全屏 + 屏幕常亮。

**控制本机**：点页面上的「控制本机」按钮 → 触摸即控制鼠标；长按 500ms = 右键；
键盘输入直接转发（需宿主带 `--allow-input`）。

### 3.3 参数速查

| 参数 | 作用 |
|---|---|
| `--display <子串>` | 选显示目标（匹配 label / 设备路径 / 适配器 ID） |
| `--mode WxH[@Hz]` | 切换虚拟屏模式，如 `1280x720@60`。**不传则不动桌面布局** |
| `--fps N` | 编码帧率 |
| `--bitrate K` | 目标码率（kbps） |
| `--no-cursor` | 采集时不合成鼠标光标 |
| `--allow-input` | 允许接收端控制本机（默认关） |

虚拟屏可用分辨率（实测枚举）：`800x600` / `1280x720` / `1366x768` / `1920x1080` /
`2560x1440` / `3840x2160`，各档均支持 30/60/90/120/144/165Hz。

## 四、已知限制（如实记录）

### 4.1 1220x720@60fps 编码吞吐不足（实测）

| 分辨率×帧率 | 采集帧数 | 编码产出 | 产出率 |
|---|---|---|---|
| 800x600@60 | 216176 | 216176 | 100% |
| 1280x720@60 @2500kbps | 216172 | 202012 | **93.5%** |
| 1280x720@60 @1500kbps | 216152 | 201873 | **93.4%** |

产出率与码率无关，是「1280x720 单帧 3.7MB × 60fps = 221MB/s」超出当前
D3D11 回读 + QSV 编码的吞吐。**建议该分辨率配 30fps**（编码压力减半）。

### 4.2 华为平板渲染上屏帧率上限约 30-35fps

实测（华为平板 + 华为浏览器）：

| 发送帧率 | 上屏帧率 | `framesDecoded` | `framesDropped` |
|---|---|---|---|
| 20 fps | 13-14 | = framesReceived | 0 |
| 60 fps | 29-35 | = framesReceived | 0 |

解码完整、无丢帧，是渲染层主动跳帧。已排除：智能刷新率（固定 120Hz）、
非整数缩放（1:1 原始尺寸）、光标合成（`--no-cursor`）、DPI（100%）、
全屏节流。属设备/浏览器限制，非宿主可解。

**静止画面完全不抖、文字清晰**，桌面/文档/代码场景可用。

### 4.3 画质协商未真正闭环

见 2.1：只上报建议，不自动改码率。真正的自适应需要进程内编码器。

### 4.4 键盘映射仅覆盖常用键

`KEYMAP` 覆盖回车/退格/方向/功能键/字母数字，未覆盖组合键修饰符语义
（如 `Ctrl+C` 会分别按下 Ctrl 和 C，多数场景可用，但少数需要修饰符状态机的应用可能异常）。
