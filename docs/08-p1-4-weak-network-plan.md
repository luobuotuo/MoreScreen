# P1.4 弱网与稳定性测试方案

> 起草日期：2026-11-21
> 对应路线图：[04-roadmap.md](04-roadmap.md) 第 104~111 行「P1.4 弱网与稳定性」
> 定位：进入 P3（产品化）之前的最后一道技术门槛。**本文是方案，不含代码改动**。

---

## 一、目标

回答一个问题：**在真实家用/办公 Wi-Fi 条件下，这块"第二屏"能不能用？**

具体要证明四件事：

1. 带宽不足时，系统是**降级**（画质变差但可用）还是**雪崩**（延迟堆积到没法操作）；
2. 有延迟和丢包时，画面是**可用**还是**卡死**；
3. 网络断开（切 Wi-Fi、平板锁屏）后，能否**自动恢复**；
4. 连续跑 8 小时，内存与队列**不持续单向增长**。

## 二、验收判据（含对 roadmap 的修正，需确认）

原 roadmap 判据有一条当前**物理上做不到**，必须重新定义。

| 编号 | 原判据 | 现实约束 | 建议判据（以现状为准） |
|---|---|---|---|
| P1.4.1 | 限速 2/5/10Mbps，**降码率**而非堆积延迟 | 编码由外部 ffmpeg 完成，码率 `-b:v` 固定，**不支持运行时改**（见 `06-p2-completion.md` 2.1） | 限速下 **jitterBuffer ≤ 300ms 且不单调增长**、不卡死、画面降级可辨认；记录实际码率 vs 限速值。**自动降码率归入 P4**（需进程内编码器） |
| P1.4.2 | 注入 20/50/100ms 延迟、1/3/5% 丢包，画面可用或明确降级 | 无自动重传策略可调（依赖 RTX/NACK 默认行为） | 丢包 ≤5% 时画面可用（无长期花屏）、RTT 与 jitterBuffer 可解释；>5% 时明确降级不静默卡死 |
| P1.4.3 | 断线重连 5 秒内恢复 | **已实现自动重连**（2026-11-21）：失败即重建整条会话，`disconnected` 给 2 秒自愈窗口，指数退避 0.5→3s，上限 20 次 | 断开后 ≤5 秒自动恢复画面；重连瞬间黑屏属预期（重新 ICE/DTLS 握手） |
| P1.4.4 | 8 小时长稳，内存/队列无单向增长 | 后台任务会被环境清理（实测 25 分钟被终止），需用常驻方式运行 | 宿主 WorkingSet 8h 增长 <10%、接收端不崩、jitterBuffer 无持续爬升 |

> **需你确认**：P1.4.1 是否接受"降级不雪崩"作为通过标准（而非"自动降码率"）。
> 若不接受，就必须先把"进程内编码器"提前到 P1.4 之前做——那是数天量级的工程。

## 四、弱网注入手段（三选一）

| 方案 | 做法 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| **① Clumsy**（Windows 工具，基于 WinDivert） | 图形界面按进程/端口注入 lag / drop / throttle | 免开发，参数直观，能立刻用 | 依赖第三方；不可脚本化回归；部分安全软件拦截驱动 | **首轮快速验证** |
| **② 自研 UDP 中继** | 先固定 ICE 端口范围，再在宿主与客户端之间插一层 UDP 代理，按参数延迟/丢包/限速 | 可脚本化、可复现、可进 CI | 需先做缺口 A；约半天开发 | 需要回归时 |
| **③ 路由器/手机热点 QoS** | 在路由侧限速 | 最接近真实 | 无法精确注入丢包/延迟，不可重复 | 只做"真实环境抽检" |

**建议路径**：先用 ① 在 1 小时内拿到 P1.4.1/P1.4.2 的结论；若结论是"需要反复回归"，再做 ②。

### 4.1 Clumsy 过滤条件

WebRTC 走 UDP（host candidate，端口随机）。因缺口 A，无法按端口过滤，改用**进程过滤**：

- 目标进程：`rs-host.exe`
- 方向：双向（inbound + outbound）
- 注意：只影响这台宿主上的 UDP；TCP 信令（8787/8788）**不要**一起限，否则会把信令也打瘫，混淆结论。

> 若 Clumsy 版本不支持进程过滤，则必须先做缺口 A（固定端口 50000~50100），再按端口过滤。

## 五、用例设计

### P1.4.1 带宽限制（2 / 5 / 10 Mbps）

| 项 | 内容 |
|---|---|
| 前置 | 单客户端、`1280x720@30 --fps 30 --bitrate 1500`、静止画面 |
| 步骤 | 依次把带宽限制设为 **2 / 1 / 0.5 Mbps**，每档稳定运行 **60 秒**（原 roadmap 的 10/5/2 远高于 1.5 Mbps 码率，测不出任何降级，已下调） |
| 观测 | 宿主 3 秒一条的质量日志；接收端页面统计；记录 `上屏fps / 丢包% / RTT / 缓冲` 的**首值、峰值、末值** |
| 通过 | 缓冲 ≤300ms、不单调增长（末值 ≤ 峰值 ×1.2）、不卡死、画面仍可辨认 |
| 记录 | 每档填一行表格（见六、模板） |

预期风险：2 Mbps 低于编码目标 1500kbps 时，**没有降码率机制**，会直接丢包 → 可能出现花屏/卡顿。这正是要量化的"雪崩边界"。

**实测结论（2026-11-21，华为平板 + Clumsy 过滤 UDP）**：

| 档位 | 上屏 | 丢包 | 缓冲 | 判定 |
|---|---|---|---|---|
| 基线（无限速） | 30fps | 0% | 13~25ms | — |
| **2 Mbps** | 30fps | 0% | 18~28ms | ✅ 通过 |
| **1 Mbps** | 30fps | 0% | 52 → **59（峰）** → 51，见顶回落 | ✅ 通过（降级不雪崩） |
| **0.5 Mbps** | 0fps | 85% | 12 → 1711 → **3469ms** | ❌ 雪崩，**约 5 分钟后自愈** |

**结论：当前架构的可用带宽下限 ≈ 1 Mbps（约码率的 2/3）。**

低于该值、又没有降码率机制时必然雪崩：丢包 85%、H.264 缺参考帧无法解码 → 0fps，
jitterBuffer 堆到 3.5 秒且**不再回落**。

**雪崩恢复实测**：停掉限速后画面 20 秒内回到 30fps，但缓冲从 3469ms 退回 126ms
耗时约 **5 分钟**（单调下降、零反弹）。浏览器 jitterBuffer 只能渐进收缩，网页无法直接控制。

**已加兜底（2026-11-21）**：接收端"高延迟看门狗"——缓冲 >1000ms 持续 10 秒即主动重建
会话（复用自动重连，黑屏 2~3 秒换取立即恢复），每页最多 3 次。

### P1.4.0 RTX 重传修复（2026-11-21，P1.4.2 的前置条件）

**症状**：3% 丢包下接收端显示 `重传 0 / 1564`——NACK 发了一千多次，宿主一次都没补。

**排查链（每一步都排除了一个假设）**：

| 步骤 | 观测 | 结论 |
|---|---|---|
| 1. NACK 是否到达宿主 | `[rtcp] nack` 从 0 涨到 635+ | RTCP 读取路径正常 |
| 2. SSRC 是否匹配 | 本端 `ssrc=2593604378` == NACK `media_ssrc: 2593604378` | 不是 SSRC 问题 |
| 3. `bind_local_stream` 是否被调用 | 在 vendor 里加日志 → `bind ssrc=... nack_supported=false feedback=[]` | **根因命中** |

**根因**：webrtc-rs 建 `StreamInfo` 时用的是 **track 自己的 codec**（`rtp_sender/mod.rs:480`），
而不是 transceiver 协商出的那份。本项目给 `TrackLocalStaticSample` 传的 codec 里
`rtcp_feedback: vec![]` 是空的 → `stream_support_nack()` 返回 false →
`nack::Responder` **连重传缓存都不建** → 后续 NACK 查表 miss 后**静默 return**（无日志无报错）。
注册给 `media_engine` 的那份（带 nack）只影响 SDP 协商，管不到这条路径。

**修复分两层**：

1. **补 track codec 的 `rtcp_feedback`**（`webrtc.rs`）→ 缓存能建起来了，日志变为
   `nack_supported=true feedback=[("transport-cc",""), ("nack",""), ("nack","pli")]`；
2. **重传必须走 RTX**（vendor `nack::Responder`）：原实现直接重发原包（原 SSRC / PT 102），
   但 SDP 一旦协商了 RTX，浏览器只认 RTX 流上的重传，原 SSRC 的旧序号被当重复包丢弃
   （A/B 实测：关掉 RTX 后重传仍为 0）。按 RFC 4588 改写为
   **RTX SSRC + PT 96 + 独立递增序列号 + payload 前置 2 字节原序列号**。

**实测结果（2026-11-21，Clumsy Drop 3% Outbound）**：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 重传（收到/发出 NACK） | 0 / 1564 | **498 / 263** |
| 上屏 | 30fps | **30fps（稳定，无花屏）** |
| 缓冲 | 24ms | 11~28ms |
| 丢包（累计） | 0.0x%（Drop 未真正生效时） | 3.27% |

「收到重传 > 发出 NACK」是正常的：一个 `TransportLayerNack` 可携带多个 nack pair（多个序号请求），
因此一次 NACK 会触发多次包重传。

> **口径提醒**：`packetsLost` 是累计值，补回的包一般不会从计数里回减，所以 3.27% 不下降
> 不等于仍在丢。判断重传是否真有效请看 **「重传」计数是否增长 + 画面是否花屏**，而不是丢包率是否归零。

**口径验证（2026-11-21，取消 Drop 勾选后）**：丢包率 **4.06% → 0.97% 单调下降、零反弹**
（每 3 秒一条，全程约 2 分钟）。确认 3.27% 属历史累计，重传补回真实有效。

### P1.4.0-b 实测缺陷：切后台回来后解码卡在 2fps（已加自愈）

**现象**（2026-11-21 实测）：接收端切走再切回，上屏帧率从 30fps 掉到**恒定 2.0fps**，
且 `document.hidden === false`（页面已在前台），宿主日志无「页面后台」标注 → **不是节流假象，是真解码降速**。

**判定过程**：先怀疑「息屏/页面后台」，但用户确认屏幕一直亮着；
为此给质量上报加了 `bg` 标记（`webrtc.html` → 宿主 `[ctl] 质量` 打印「页面后台，帧率冻结」），
实测该标注**不出现**，排除后台节流 → 确认为内核停在「低帧率节能解码」且不自行恢复。

**自愈措施（三层，逐级加重）**：

| 层级 | 触发 | 动作 | 代价 |
|---|---|---|---|
| 1 | 从后台恢复 | 重置帧率差分基准 + `video.play()` | 无 |
| 2 | 可见且 `fps < 8` 持续 5s | **重挂视频轨**（摘掉 srcObject 再挂回，强制重建解码管线），最多 2 次 | 无黑屏 |
| 3 | 重挂 2 次仍 <8fps | 重建会话（复用自动重连），每页一次 | 黑屏 2~3s |

恢复后 `remountCount` 归零，下次再进后台仍可重挂。

**实测验证（2026-11-21）**：切走 5 秒再切回 → 页面底部日志出现
`⚠ 上屏 X.Xfps 持续 5s，重挂视频轨（第 1/2 次）` + `视频轨已重挂` → 帧率恢复 30fps。第 2 层即生效，未用到重建会话。

> **前置坑（同日定位）**：`serve.rs` 原响应头**没有 `Cache-Control`**，浏览器启发式缓存导致
> 「改了前端、刷新后仍跑旧代码」——自愈代码第一轮因此完全没加载。已改为 `no-store`。

> 该缺陷对 **P1.4.4 的 8 小时长稳测试是必然干扰项**：长时间运行难免切后台，
> 若不区分「后台冻结」与「解码降速」，会得到一批假故障数据。`bg` 标记与自愈均已落地。

**附带观测：后台期间 jitterBuffer 只进不出**。页面在后台时 video 元素不消费数据，
实测缓冲 `38 → 95 → 144 → 196 → 254 → 284 → 315ms` 单向爬升（丢包率与 RTT 同步失真）。
这不是链路问题，但会成为长稳测试的假阳性来源——**P1.4.4 必须保证页面全程在前台**，
并在数据清洗时剔除带「页面后台」标注的样本。

### P1.4.2 延迟与丢包注入

| 项 | 内容 |
|---|---|
| 组合 | 延迟 20 / 50 / 100ms × 丢包 1% / 3% / 5%，共 9 组 |
| 每组件 | 稳定 45 秒 |
| 观测 | 同 P1.4.1；另记录**操作跟手性**（主观：拖动窗口是否明显滞后） |
| 通过 | 丢包 ≤3%：无长期花屏；丢包 5%：画面降级但不静默卡死；延迟 100ms 时仍可操作（主观可接受） |

**实测记录（2026-11-21，Clumsy 只勾 Outbound，RTX 重传已修复）**

| 组 | Lag | Drop | 上屏 | 丢包 | RTT | 缓冲 | 判定 |
|---|---|---|---|---|---|---|---|
| A1 | 20ms | 3% | **28.8~31.1fps** | 3.1~3.6% | **32~64ms**（基线 6~19） | **18~26ms** | ✅ 通过 |
| A2 | 50ms | 3% | **28.0~32.2fps** | 3.01~3.09% | **58~88ms**（尖峰 105） | 28 → **68（峰）→ 64**，见顶回落 | ✅ 通过 |
| A3 | 100ms | 3% | **29.8fps** | **3.07%** | **220ms**（基线 20 + 单向 100×2） | **144ms** | ✅ 通过 |

A3 备注（2026-11-22，1080p30 + Clumsy outbound/udp，会话 #10 截图实证）：
- RTT 220ms 与 Lag 100ms 单向**精确对上**（200 + 基线 20），说明是纯延迟注入而非队列积压；
- 3.07% 丢包下上屏 **29.8fps 不掉帧**（帧 2151/2276 丢 60），RTX 重传 4092/1524 正常工作；
- 缓冲 **144ms**，远低于 300ms 判据，无雪崩迹象；画面肉眼可用。
- **吞吐疑问的结论要分两段看（2026-11-22 晚修正）**：
  - **宿主编码侧通过**：1920×1080@30（≈6220 万像素/秒）编码稳定 29.8fps、3.08Mbps；
  - **华为平板解码渲染侧不足**：同参数下 header 帧率（framesDecoded）26.2fps，但
    【上屏】（requestVideoFrameCallback）只有 **15.8fps**、缓冲 **374ms**、丢帧 324/1964（16.5%）。
  - 结论：**1080p30 不是可用配置**，平板实际能力约 720p30；分辨率需按接收端能力降级
    （归入 P2.1 自适应 / P3 产品化决策），`docs/06 §4.1` 的「高分辨率吞吐不足」**仍然成立**，
    只是瓶颈在接收端解码渲染而非宿主编码。
- **暴露并修复一个测量缺陷**：接收端「玻璃到玻璃」一直显示「同步中」——宿主侧 `json_str` 只解析
  带引号的字符串，而接收端 sync 请求发 JSON 数字 `"c":12345` → 取不到 → 回包 `c=0` →
  接收端算出 rtt 数千秒被过滤 → 偏移估计永不成立。修复：接收端改发字符串（`String(...)`）+
  宿主优先 `json_num` 解析 + 弱网下每 5 秒重试同步、成功后每 60 秒刷新。

A2 备注（165 秒有效采样，数据最完整的一组）：
- 缓冲完整记录到收敛全过程：`28 → 39 → 49 → 60 → 68（峰，横住约 30 秒）→ 67 → 66 → 65 → 64`；
- RTT 增量 ≈ +50ms，与 Lag 设定一致，说明是纯延迟而非队列积压；
- 3% 丢包下上屏仍 30fps，RTX 重传持续补齐。

A1 备注：
- 有效采样 24 秒（8 个点），后半段因切后台/刷新作废，趋势稳定；
- 3% 丢包下**上屏不掉帧**，是 RTX 重传修复的直接效果；
- 另一段低丢包期（1.9%→0.3%）缓冲 `35→56ms` 后**横在 56ms**，再次印证收敛而非爬升。

### P1.4.2-b 实测缺陷：连接早期输入回传「假就绪」（2026-11-21 已修复）

**现象**：Clumsy 未 Start（正常网络），接收端显示已连接并处于「控制本机」状态，
点击被采集画面里的宿主机任务栏图标，**宿主物理屏也没有任何响应**；约几十秒后再次点击才生效。
宿主物理屏无响应 ⇒ 排除「输入生效但回显冻结」，确认输入消息根本没送达。

**排查链（逐条用代码证据排除）**：

| 假设 | 证据 | 结论 |
|---|---|---|
| 坐标映射越界 | `contentRect()` 在 videoWidth=0 时退回元素矩形（`webrtc.html:170`），不会返回 null | 排除 |
| 输入开关未开 | 缺 `--allow-input` 会**全程**无效，不会出现「几十秒后生效」 | 排除 |
| 信令未下发 offer | `serve.rs:65` WS 连接即登记 joined；`webrtc.rs:556` 已打印「offer 已生成…耗时 X ms」 | 非主因 |
| 回显冻结 | 宿主物理屏无响应 | **排除** |
| **控制通道未就绪时消息被吞** | `ctlSend` 原实现在 `dc.readyState !== 'open'` 时直接 return，无提示无排队 | **命中** |

**根因（三层）**：

1. `ctlSend`（原 `webrtc.html:137`）在 DataChannel `open` 之前静默丢弃所有消息；
2. 「控制本机」按钮在点「开始接收」瞬间即可点（`webrtc.html:560`），开启时不检查 dc 状态，
   还打印「输入回传已开启」——**假就绪**。用户在 SCTP/DCEP 握手完成前的点击全部失踪，
   直到 `dc.onopen` 才生效，表现为「几十秒后有反应」；
3. 放大器：`doReconnect()` / `buildPeerConnection()` 均未把 `dc` 置空，重连后 `dc`
   仍可能指向已关闭的旧通道，输入继续发进黑洞；`ctlSend` 的 `catch {}` 也吞掉了发送异常。

**修复（2026-11-21）**：

| 层 | 改动 |
|---|---|
| 按钮 | 初始 `disabled` + 文案「控制通道连接中…」；只在 `dc.onopen` 后启用 |
| `ctlSend` | input 类丢弃并给出节流提示（**不排队回放**，避免几十秒攒下的按下/抬起一次性打进主机）；stat 静默丢弃；device/hello 进有界 8 条队列，`onopen` 补发；发送异常改为可见日志 |
| 生命周期 | 新增 `resetControlUI()`，`buildPeerConnection` / `doReconnect` / `onclose` 三处统一复位 `dc` / `inputOn` / 按钮；`onopen` / `onclose` 用 `dc !== ch` 守卫旧通道迟到事件 |
| 诊断打点 | 接收端打印 `ondatachannel` 的 readyState 与「控制通道已就绪（开始接收后 X.Xs）」；宿主打印「收到首条输入消息」；`--allow-input` 缺失时改为显式告警而非静默 return |

**验证口径（下一轮实测）**：

- 页面日志「收到控制通道（readyState=connecting，开始接收后 Xs）」→「控制通道已就绪（…Ys）」，
  Y−X 即 SCTP/DCEP 握手耗时，用于定位「几十秒」耗在 ICE/DTLS 还是 SCTP；
- 宿主侧「offer 已生成…耗时 Z ms」（`webrtc.rs:556`）与 Y 对齐，可区分慢在 offer 阶段还是握手阶段；
- 未就绪期间点击应看到「⚠ 控制通道未就绪，本次操作未发送」，而**不再**无声无息。

> **与 P1.4.0-b 的区别**：那一例是「解码降速」，靠重挂视频轨自愈；本例是「控制消息丢失」，
> 任何重挂/重连都救不了，必须改通道就绪语义。

### P1.4.2-c 实测缺陷：静止采集导致 fps 大幅波动 + 周期性黑屏（2026-11-21 已修复）

**现象**：修完 P1.4.2-b 后实测，上屏 fps 在 **0~26 之间大幅波动（多数时间 10~15）**，
且**每隔十几到二十秒画面变黑并重启**。

**先划清因果边界**：P1.4.2-b 的改动只触及控制通道（`ctlSend` / 按钮 / `resetControlUI`），
`git diff` 自证视频采集、编码、RTP 发送、解码、统计路径**零改动**。
因此 fps 波动与黑屏不是该次改动引入，而是**问题 1（静止采集）在发作**。

**两个症状、两条机制**：

| 症状 | 机制 | 代码 |
|---|---|---|
| fps 0~26 波动 | 采集链路纯「采集源驱动」：WGC 只在画面变化时给帧。静止→0fps，有操作→26fps，平均 10~15 | `capture.rs` `TryGetNextFrame` 空帧分支原本只有 `sleep(2ms)` |
| 每十几~二十秒黑屏重启 | 低帧自愈三级动作的固定节奏：fps<8 持续 5s → 重挂视频轨（黑一下）→ 再 5s → 第 2 次重挂 → 再 5s → 重建会话（黑 2~3s），合计约 15s | `webrtc.html` 自愈段 |

即：**源头无帧 → fps 跌破 8 → 自愈反复重挂/重连 → 周期性黑屏**。自愈治的是解码卡住，
对「发送端没帧」完全无效，只会白黑屏。

**修复（2026-11-21）**：

1. **采集端静止保活**（`capture.rs`）：缓存上一帧 BGRA，空帧分支里若距上次送帧已超过
   目标帧间隔，就重复送上一帧。编码器对相同帧只输出极小的 skip P 帧，码率几乎不增，
   但接收端上屏帧率恒定、交互回显即时。保活帧单独计 `keepalive_frames`，**不计入** `frames`，
   避免「采集结束: N 帧 / X fps」被虚高；`target_fps=0` 时退回 ~30fps，防止 2ms 空转。
   影响面：`capture_stream` 的两个调用点（`main.rs:329` 旧 WS `stream`、`main.rs:735` `stream-webrtc`）均受益。
2. **自愈加源头判别**（`webrtc.html`）：`fps<8` **且** 码率 <50kbps 时判定为「采集端无新帧」，
   只标注、不重挂不重建，杜绝无意义的周期性黑屏。

**验证口径**：
- 画面静止不动时，上屏 fps 应稳定保持在目标帧率附近，而不是 0~2；
- 宿主结束采集时新增一行「其中静止保活补帧: N 帧」，N>0 即证明保活生效；
- 静止期间不应再出现「重挂视频轨」「重建会话以恢复解码」日志。

### P1.4.2-d 实测缺陷链复盘：点击无响应的根因分层与观测补全（2026-11-21）

**现象演进**（同一问题的三个面具）：
1. 连接早期点击宿主机图标无响应，几十秒后恢复（P1.4.2-b）；
2. 修完假就绪后：**按钮（控制本机）本身点不动**——一直灰显。

**方法论反思（用户点名批评「代价太大」）**：前几轮修复都是在**没有端到端观测**的情况下
基于代码推理打补丁，每轮只消除一个候选根因，症状换个面具继续出现。正确做法是先把
「点击无响应」的链路拆层、逐层建立可观测证据，再谈修复。

**链路分三层**：

```
浏览器事件 → normCoords → ctlSend → [SCTP/DataChannel] → 宿主 on_message
            → handle_ctl → [SendInput] → Windows UIPI → 目标窗口
```

**第 2 个面具的确定性根因（本轮代码定位）**：`ondatachannel` 事件派发若晚于 SCTP 流
open（事件排队延迟是真实存在的），注册的 `ch.onopen` 就**永远错过** open 事件——
按钮启用逻辑绑在 onopen 上 → 按钮永久禁用。这是 P1.4.2-b 修复自身引入的回归。
修复：注册后立刻检查 `readyState === 'open'` 兜底调用一次。

**「几十秒」原始根因的判定矩阵**（三种候选，三层观测各钉死一个）：

| 候选根因 | 观测点 | 钉死方式 |
|---|---|---|
| A. SCTP/DataChannel 通道迟迟未建立（DCEP 慢/事件派发晚） | 接收端 header 新增「控制通道」状态 + echo 回环延迟 + 「控制通道已就绪（开始接收后 Xs）」 | 状态长期「握手…/连接中」或就绪耗时达几十秒 |
| B. SendInput 被 Windows 拒绝（UIPI：目标是提权窗口/部分系统 UI） | `input.rs` 新增 `send_input_checked`：注入条数不足即打印 `GetLastError`（5=拒绝访问） | 宿主终端出现 `[input] SendInput 失败` |
| C. 通道 open 但消息丢失（旧黑洞类问题） | echo 回包：`{"t":"echo"}` 原样回 `{"t":"echo-ok"}`，前端显示回环毫秒数 | echo 通但无 `[input] 失败` → 问题在坐标/焦点等应用层 |

**改动清单（2026-11-21）**：
- `webrtc.html`：`onOpen` 提为具名函数 + `readyState` 竞态兜底；header 增加「控制通道」
  状态（— / 连接中 / 握手… / open / open·Nms / closed）；onopen 后自动发 echo。
- `main.rs`：hub_pump 收到 `{"t":"echo"}` 时经 `rtc.deliver` 原样回 `echo-ok`
  （与 `handle_ctl` 解耦，不碰输入逻辑）。
- `input.rs`：`send_input_checked` 检查 `SendInput` 返回条数，失败打印 `GetLastError`。

**验证口径（一次真机测试即可钉死根因）**：
刷新页面 → 看 header「控制通道」从「连接中」到「open·Nms」的过程与耗时；
开启控制点一个**普通**窗口的按钮 → 若无反应，按上表 A/B/C 三行对照日志，
**哪一个观测点亮了，根因就是哪一层**——不再需要下一轮猜测。

### P1.4.2-e 僵尸会话回收（2026-11-22 修复）

**症状（4h 服务日志实证）**：客户端 #2 ICE `conn=Failed` 后，宿主仍按 33ms 节拍持续
`write_sample` 写入 38 万帧（≈3.5 小时空转）——连接已死但编码/打包线程照跑，CPU 白烧。
这也解释了用户观察到的宿主 CPU 95%：每失败一个客户端就多一路空转编码分发。

**根因（两层）**：
1. `run_once` 主循环只处理信令/帧，**从不检查 pc 连接状态**——Failed 后循环永续；
2. 会话线程即使退出，`SessionHandle` 仍留在 Hub 的 sessions map：同 id 客户端重连时
   `join` 幂等检查撞上死句柄（信令投进黑洞、永不重建）。

**修复（`webrtc.rs` 三处）**：
- `run_once` 5b 节拍分支开头检测 `connection_state() == Failed`：首次记录时刻并告警，
  持续 10s 无恢复即 `pc.close()` + return（`failed_since` 计时，恢复即清零）；
  `Disconnected` 是弱网暂态（客户端自动重连可恢复），不回收；
- `join` 会话线程退出路径（含 tokio 运行时创建失败）统一 `sessions_map.remove(&id)`，
  与 `leave()` 双向幂等 remove。

**验证口径**：真机断开平板网络 >10s，宿主日志应依次出现「连接状态 Failed：10 秒内无恢复
将回收会话」→「Failed 持续 10s，回收僵尸会话（累计写入 N 帧）」；随后平板恢复网络、页面
重连，新会话应正常建立（同 id 不再撞死句柄）。编译校验：`cargo check --release` 通过。
